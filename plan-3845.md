# Implementation plan for issue #3845

## Goal

Add a high-level, generic node-location selector without changing the existing
`mapdl.nsel()` API. The implementation should support arbitrary user-provided
coordinate values and should work with the existing local and remote MAPDL
connection modes.

The material-construction suggestion in the issue discussion is kept as a
separate workstream. It should not be coupled to the selector implementation
because it has a different API, validation model, and command mapping problem.

Implementation must follow a test-first workflow. The selector contract and
expected command composition are written as tests before production code is
added. The implementation is then developed until those tests pass, followed
by integration and regression validation.

## Proposed API

Expose a lazily created selector object:

```python
mapdl.selector.select(
    x=...,
    y=...,
    z=...,
)
```

The public method should:

- target nodes in the first implementation;
- accept any subset of `x`, `y`, and `z`;
- use case-insensitive coordinate names if the API also accepts keyword
  aliases;
- update MAPDL's current node selection;
- retain the existing MAPDL selection tolerance behavior unless the caller
  explicitly supplies a supported tolerance option;
- follow an explicit default selection mode, with additional modes added only
  if they can be mapped unambiguously to `NSEL` semantics.

The criterion normalization must be defined before coding:

- a scalar means one coordinate value;
- a collection means an OR of its values;
- an interval means an inclusive lower/upper bound;
- open-ended intervals and floating-point intervals should have an explicit
  representation;
- Python `range` must not be treated ambiguously. Its stop-value behavior
  differs from MAPDL's inclusive selection ranges, so the supported behavior
  must be documented and tested.

The method should reject a call with no criteria and should raise clear
`ValueError` or `TypeError` exceptions for unsupported or ambiguous input.

## Implementation steps

### 1. Write the tests first

Before adding the selector module or public property, add focused unit tests
using mocks or command capture. The initial failing test set should cover:

- one scalar criterion;
- criteria on two and three axes;
- multiple discrete values on one axis;
- an inclusive interval;
- mixed discrete and interval criteria;
- arbitrary values unrelated to the issue's example;
- empty, reversed, nonnumeric, and unsupported criteria;
- correct AND/OR composition;
- cleanup of temporary components after success and after an exception;
- preservation of existing `nsel()` behavior.

These tests establish the public input semantics, selection-mode behavior,
return value, generated MAPDL commands, and error behavior before the
implementation is written. Do not weaken or remove a test merely to make an
implementation pass; update the contract only when the behavior is
deliberately reconsidered.

### 2. Add the selector abstraction

Create a non-generated selector module under
`src/ansys/mapdl/core/`, containing a small selector class that keeps a
reference to the owning MAPDL instance.

Add a lazy `mapdl.selector` property in the normal PyMAPDL implementation
layer. Do not modify anything under
`src/ansys/mapdl/core/_commands/`; those files are generated.

Define typed internal representations for normalized coordinate criteria so that
command generation does not need to inspect arbitrary Python objects.

### 3. Normalize and validate criteria

Implement one normalization path for scalar values, collections, and intervals.
It should:

- normalize coordinate names to `X`, `Y`, and `Z`;
- reject strings and mappings when they are accidentally supplied as iterable
  coordinate values;
- preserve numeric types accepted by MAPDL;
- detect empty collections;
- detect reversed or otherwise invalid bounds;
- make inclusive/exclusive boundary behavior explicit;
- produce deterministic criteria for testing.

Document the selected interval syntax and the treatment of `range` before
exposing the method as public API.

### 4. Translate criteria into MAPDL selections

Build the selection engine on top of existing `NSEL`, `CM`, and `CMSEL`
operations rather than duplicating MAPDL selection logic.

The implementation must preserve the logical meaning of the request:

- alternatives within one axis are combined with OR;
- different axes are combined with AND;
- temporary components or an equivalent scoped mechanism are used when a
  direct sequence of `NSEL,A` and `NSEL,R` commands would otherwise lose the
  intersection with earlier criteria;
- temporary names are unique and are deleted on both success and failure;
- the final selection remains active after the helper returns;
- the implementation does not accidentally restore the caller's previous
  selection unless that is explicitly part of the selected mode.

Use existing selection-tolerance behavior instead of comparing coordinates in
Python with exact floating-point equality. Keep the command path compatible
with both local and remote connections.

### 5. Define return and selection-mode behavior

Match the existing PyMAPDL conventions for selection command results. Decide
and document whether the helper returns the selected node IDs, command output,
or both through an established result type.

If append, reselect, and unselect behavior is included, map each mode directly
to documented MAPDL semantics and test it independently. If the issue only
requires creating a new selection, keep the first implementation limited to a
new-selection default and avoid speculative modes.

### 6. Run integration and regression validation

Use the tests written in step 1 to drive implementation until they pass.
Then add a small integration test using the repository's existing MAPDL
fixtures if the command-composition behavior cannot be fully verified with
mocks. Run the existing selection tests unchanged to verify backward
compatibility.

### 7. Add documentation

Add numpydoc documentation and examples for the selector property and method.
Explain:

- the accepted criterion forms;
- scalar, OR, and AND semantics;
- coordinate tolerance;
- the resulting MAPDL selection state;
- the distinction between coordinate selection and explicit node-ID
  selection.

Do not add a hand-written changelog fragment under `doc/changelog.d/`; CI
generates those fragments from the pull request.

## Separate material workstream

If the issue owner decides that the material suggestion is part of issue #3845,
implement it separately after the selector API is stable:

1. Add a non-generated `mapdl.materials` manager.
2. Define the supported `new()` signature and property aliases, including the
   mapping from `nu` to the appropriate MAPDL property label such as `NUXY`.
3. Validate material IDs, property names, and values.
4. Emit the existing `MP` commands through the generated command wrappers.
5. Define whether `new()` requires an ID or allocates one, and return the
   resulting material ID.
6. Add tests for alias mapping, multiple properties, invalid input, and command
   ordering.
7. Document the supported linear properties and explicitly defer nonlinear
   `TB` material models unless they are included in the agreed scope.

This workstream should be split into a separate issue or pull request if the
material API requirements remain undefined.

## Validation and completion criteria

Before considering the selector implementation complete:

- targeted selector tests pass;
- the changed source passes the repository's formatting, typing, and linting
  checks;
- the public API documentation builds or passes its targeted checks;
- existing selection tests pass unchanged;
- no generated command file is modified;
- no changelog fragment is added manually.
