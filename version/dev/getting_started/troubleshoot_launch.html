Launching issues#

This page helps you find why MAPDL does not launch. If you do not know the cause, start with the debugging guide. For other problems, see Troubleshooting PyMAPDL.

Debug launching issues#

When MAPDL fails to launch, PyMAPDL usually raises a generic error such as MapdlDidNotStart or LaunchError. The cause is normally recorded in the PyMAPDL log and in the files that MAPDL writes to its working directory. To find it, follow these steps.

Step 1: Record the PyMAPDL log#

Write the log at the DEBUG level to a file before calling the launch_mapdl() function:

from ansys.mapdl.core import LOG, launch_mapdl

LOG.setLevel("DEBUG")
LOG.log_to_file("pymapdl_launch.log")

mapdl = launch_mapdl(loglevel="DEBUG")

The log contains the resolved configuration (executable file, version, port, and number of processors), the working directory, and the exact command used to start MAPDL.

Step 2: Find the working directory#

MAPDL writes its files, including the error and output files, to its working directory. By default, PyMAPDL creates a new temporary directory for each launch, named ansys_ followed by a random string, and does not delete it on exit. You can find it in one of these ways:

  • Set it yourself. Use the run_location argument to launch MAPDL in a known directory:

    import os

run_location = os.path.join(os.getcwd(), "mapdl_debug")
mapdl = launch_mapdl(run_location=run_location, loglevel="DEBUG")

    If a previous session ended abnormally, a file.lock file might block the new launch. Delete it, use a new directory, or pass override=True.

  • Read it from the log. Search for the Location: entry.

  • Query it from a running session. Use the Mapdl.directory property.

  • Look in the system temporary directory. Find the most recently modified ansys_* directory.

Step 3: Inspect the files in the working directory#

Some files start with a dot (.), so they might be hidden. Use ls -a on Linux. The file prefix is the job name, which you can change with the jobname argument.

  • .__tmp__.out (Windows only): MAPDL console output. If the launch is successful, it contains the START GRPC SERVER banner described in Debug PyMAPDL. Otherwise, it usually contains the reason for the failure, such as licensing or MPI errors.

  • .__tmp__.inp (Windows only): Temporary input file that starts MAPDL in batch mode. It contains only the FINISH command.

  • file.err and file0.err: MAPDL error and warning messages. In distributed memory parallel (DMP) mode, each process writes its own file.

  • file.out and file0.out: MAPDL output files.

  • file.lock: Lock file that exists while MAPDL is running. If MAPDL is not running and the file is present, the previous session ended abnormally.

Search these files for *** ERROR *** messages. If they contain UDS socket file already exists, see Error: UDS socket file already exists.

On Linux, PyMAPDL does not write the MAPDL console output to a file by default. To capture it, use the mapdl_output argument:

mapdl = launch_mapdl(
    run_location="mapdl_debug",
    mapdl_output="mapdl_console_output.txt",
    loglevel="DEBUG",
)

If the working directory is empty, MAPDL probably failed before it started. Check the launch command in the next step.

Step 4: Inspect the launch command#

The log shows the exact command in the Generated MAPDL command and Command: entries. Check that:

  • The executable path exists and points to the expected MAPDL version. If it does not, see Updating MAPDL installation.

  • The number of processors (-np), memory (-m), and license type (-p) are correct.

  • The port (-port) is not used by another process.

  • The additional_switches argument and the PYMAPDL_ADDITIONAL_SWITCHES environment variable do not conflict.

To reproduce the issue outside PyMAPDL, run the command from the working directory. The log shows the arguments joined by spaces, without shell quoting, so you must quote paths that contain spaces:

In PowerShell, quote the path and use the call operator (&):

PS C:\Users\user\AppData\Local\Temp\ansys_ymjqvmeyww> & "C:\Program Files\ANSYS Inc\v242\ansys\bin\winx64\ansys242.exe" -j file -np 2 -port 50052 -grpc -b -i .__tmp__.inp -o .__tmp__.out

In cmd.exe, quote the path only. The -i .__tmp__.inp argument requires that file in the working directory. If it does not exist, create it with a single FINISH line.

user@machine:/tmp/ansys_ymjqvmeyww$ /usr/ansys_inc/v242/ansys/bin/ansys242 -j file -np 2 -port 50052 -grpc

For more information, see Testing MAPDL launching.

Step 5: Inspect the environment variables#

PyMAPDL does not log the environment variables because they might contain sensitive information. Depending on the arguments of the launch_mapdl() function, PyMAPDL builds the MAPDL environment in one of these ways:

  • Default, or with the add_env_vars argument: MAPDL inherits the environment of the Python process. PyMAPDL then applies these changes in order, so later changes override earlier ones:

    1. On Ubuntu, sets I_MPI_SHM_LMT to shm.

    2. Sets ANS_CMD_NODIAG to TRUE.

    3. Adds the variables in add_env_vars, overriding any variable with the same name, including the two preceding ones.

    4. With the mtls transport mode, sets ANSYS_GRPC_CERTIFICATES to the certs_dir argument. Without it, PyMAPDL keeps the existing value or defaults to the certs directory in the current directory.

  • With the replace_env_vars argument: MAPDL receives only the variables in this argument. PyMAPDL does not set any of the preceding variables, so you must provide everything MAPDL needs, such as PATH and the license server variables.

To print the environment, working directory, and command without starting MAPDL, run the following code with the same arguments you pass to the launch_mapdl() function:

from ansys.mapdl.core.launcher.config import resolve_launch_config
from ansys.mapdl.core.launcher.environment import prepare_environment
from ansys.mapdl.core.launcher.process import _generate_launch_command

config = resolve_launch_config(nproc=2, run_location="mapdl_debug")

print("Working directory:", config.run_location)
print("Command:", " ".join(_generate_launch_command(config)))

env = prepare_environment(config).variables
for key, value in sorted(env.items()):
    if key.startswith(("ANS", "AWP", "PYMAPDL", "I_MPI")):
        print(f"{key}={value}")

Warning

These functions are internal to PyMAPDL and might change without notice. Use them only for debugging.

Check, in particular, ANSYSLMD_LICENSE_FILE and ANSYSLI_SERVERS (see Licensing issues), AWP_ROOT<version>, ANSYS_LOCK, the PYMAPDL_* variables, and the I_MPI_* variables (see Message Passing Interface (MPI) issues). For more information, see Incorrect environment variables.

Step 6: Share the information#

If you still cannot identify the issue, open a discussion on the PyMAPDL Discussions page or an issue on the PyMAPDL Issues page. Attach the PyMAPDL log and the .__tmp__.out, file*.err, and file*.out files.

Warning

Before sharing these files, remove any sensitive information, such as license server addresses, usernames, and paths.

Common launching issues#

Error: UDS socket file already exists#

On Linux, MAPDL can use a Unix Domain Socket (UDS) file instead of a TCP port to communicate with PyMAPDL. MAPDL creates this file in the UDS directory and names it mapdl-<PORT>.sock, where <PORT> is the port number. The default UDS directory is ~/.conn. To change the UDS directory, use the uds_dir argument of the launch_mapdl() function or the ANSYS_MAPDL_UDS_PATH environment variable.

If MAPDL does not launch and its output files (.__tmp__.out, file*.out, or the file set with the mapdl_output argument) contain an error like this one:

*** ERROR ***                           ELAPSED TIME =       8.394   TIME= 11:01:03
UDS socket file already exists at /home/user/.conn/mapdl-50052.sock.
   Another server may already be running on this socket.  Please try
again to start the server with a different file name by changing the
port option.

The socket file for that port already exists in the UDS directory. This happens when either of these conditions is true:

  • Another MAPDL instance is running and using that socket file.

  • A previous MAPDL instance crashed or was terminated abnormally and left the socket file behind.

To check whether a process is using the socket file, run this command:

user@machine:~$ lsof ~/.conn/mapdl-50052.sock

If the command does not print anything, no process is using the file.

To solve the issue, use one of these approaches:

  • Delete the socket file. Do this only if you are certain that no MAPDL instance is running or using that file:

    user@machine:~$ rm ~/.conn/mapdl-50052.sock

  • Use a different port. Because the socket filename includes the port number, MAPDL creates a new socket file, mapdl-<PORT>.sock, that does not conflict with the existing one:

    from ansys.mapdl.core import launch_mapdl

mapdl = launch_mapdl(port=50053)  # Uses ``~/.conn/mapdl-50053.sock``

Connection timeout#

In some networks, MAPDL might take longer than expected to connect to the license server or to the remote instance. In those cases, you might see this message:

PyMAPDL is taking longer than expected to connect to an MAPDL session. Checking if there are any available licenses...

To increase the starting timeout, use:

from ansys.mapdl.core import launch_mapdl

mapdl = launch_mapdl(start_timeout=60)

If you are connecting to a remote instance, use:

from ansys.mapdl.core import Mapdl

mapdl = Mapdl(timeout=60)

Testing MAPDL launching#

In some cases, it may be necessary to run the launch command manually from the command line.

Open a command prompt and run the version-dependent command:

(.venv) PS C:\Users\user\pymapdl> & "C:\Program Files\ANSYS Inc\v241\ansys\bin\winx64\ANSYS241.exe"

Note

In PowerShell, use the call operator (&) to run a quoted executable path. Keep the path in quotes when it contains spaces.

Run the version-dependent command:

(.venv) user@machine:~$ /usr/ansys_inc/v241/ansys/bin/ansys241

You should start MAPDL in a temporary working directory because MAPDL creates several temporary files.

You can specify a directory by launching MAPDL from the temporary directory:

(.venv) PS C:\Users\user\pymapdl> mkdir temporary_directory
(.venv) PS C:\Users\user\pymapdl> cd temporary_directory
(.venv) PS C:\Users\user\pymapdl> & 'C:\Program Files\ANSYS Inc\v241\ansys\bin\winx64\ANSYS241.exe'

Or, you can specify the directory using the -dir flag:

(.venv) PS C:\Users\user\pymapdl> mkdir temporary_directory
(.venv) PS C:\Users\user\pymapdl> & 'C:\Program Files\ANSYS Inc\v241\ansys\bin\winx64\ANSYS241.exe' -dir "C:\ansys_job\mytest1"

(.venv) user@machine:~$ mkdir temporary_directory
(.venv) user@machine:~$ cd temporary_directory
(.venv) user@machine: temporary_directory $ /usr/ansys_inc/v241/ansys/bin/ansys241

Or, you can specify the directory using the -dir flag:

(.venv) PS C:\Users\user\pymapdl> mkdir /tmp/ansys_tmp/job1
(.venv) PS C:\Users\user\pymapdl> /usr/ansys_inc/v241/ansys/bin/ansys241 -dir /tmp/ansys_tmp/job1

If this command doesn’t launch MAPDL, look at the command output:

(.venv) PS C:\Users\user\pymapdl> & 'C:\Program Files\ANSYS Inc\v241\ansys\bin\winx64\ANSYS241.exe'
*** ERROR ***
Another Ansys job with the same job name (file) is already running in this
directory or the file.lock file has not been deleted from an abnormally
terminated Ansys run. To disable this check, set the ANSYS_LOCK environment
variable to OFF.

(.venv) user@machine:~$ /usr/ansys_inc/v241/ansys/bin/ansys241
*** ERROR ***
Another Ansys job with the same job name (file) is already running in this
directory or the file.lock file has not been deleted from an abnormally
terminated Ansys run. To disable this check, set the ANSYS_LOCK environment
variable to OFF.

Incorrect environment variables#

If you are using a non-standard install, you might need to manually set the environment variables ANSYSXXX_DIR, AWP_ROOTXXX, and CADOE_LIBDIRXXX to the correct location. The three-digit MAPDL version appears where XXX is shown. For Ansys MAPDL 2024 R2, 242 appears where XXX is shown.

PS echo $env:AWP_ROOT242
C:\Program Files\ANSYS Inc\ANSYS Student\v242

PS echo $env:ANSYS242_DIR
C:\Program Files\ANSYS Inc\ANSYS Student\v242\ANSYS

PS echo $env:CADOE_LIBDIR242
C:\Program Files\ANSYS Inc\ANSYS Student\v242\CommonFiles\Language\en-us

Set these environment variables to custom values for the terminal session:

PS $env:AWP_ROOT242 = "C:\Program Files\ANSYS Inc\v242"
PS echo $env:AWP_ROOT242
C:\Program Files\ANSYS Inc\v242

PS $env:ANSYS242_DIR = "C:\Program Files\ANSYS Inc\v242\ANSYS"
PS echo $env:ANSYS242_DIR
C:\Program Files\ANSYS Inc\v242\ANSYS

PS $env:CADOE_LIBDIR242 = "C:\Program Files\ANSYS Inc\v242\CommonFiles\Language\en-us"
PS echo $env:CADOE_LIBDIR242
C:\Program Files\ANSYS Inc\v242\CommonFiles\Language\en-us

To make these changes permanent:

PS [System.Environment]::SetEnvironmentVariable('AWP_ROOT242','C:\Program Files\ANSYS Inc\v242',[System.EnvironmentVariableTarget]::User)
PS echo $env:AWP_ROOT242
C:\Program Files\ANSYS Inc\v242

PS [System.Environment]::SetEnvironmentVariable('ANSYS242_DIR','C:\Program Files\ANSYS Inc\v242\ANSYS',[System.EnvironmentVariableTarget]::User)
PS echo $env:ANSYS242_DIR
C:\Program Files\ANSYS Inc\v242\ANSYS

PS [System.Environment]::SetEnvironmentVariable('CADOE_LIBDIR242','C:\Program Files\ANSYS Inc\v242\CommonFiles\Language\en-us',[System.EnvironmentVariableTarget]::User)
PS echo $env:CADOE_LIBDIR242
C:\Program Files\ANSYS Inc\v242\CommonFiles\Language\en-us
